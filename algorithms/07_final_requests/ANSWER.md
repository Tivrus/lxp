# Диспетчер заявок: ответы и сложность

## Почему симметричный обход BST идёт по возрастанию

В BST все ключи левого поддерева меньше ключа узла, а все ключи правого больше. Симметричный обход сначала полностью выводит левое поддерево, потом сам узел, потом правое. По индукции: для пустого дерева утверждение верно; если левое и правое поддеревья выводятся по возрастанию, то "все меньшие (по возрастанию), узел, все большие (по возрастанию)" тоже идёт по возрастанию.

## Удаление узла с двумя потомками

Используется симметричный преемник, то есть минимум правого поддерева. У него нет левого потомка, поэтому его удаление сводится к случаю "лист" или "один потомок". В узел переносится вся заявка целиком, а не только id.

## Сложность

n это число заявок, h это высота дерева (от log n в сбалансированном случае до n в вырожденном).

| Операция | Время | Память |
|---|---|---|
| insert, search, delete, get_depth | O(h) | O(1) в итеративной версии, O(h) в рекурсивной |
| find_min, find_max | O(h) | O(1) |
| обходы (прямой, симметричный, обратный) | O(n) | O(h) на стек рекурсии + O(n) на результат |
| уровневый обход | O(n) | O(n) на очередь |
| count_nodes, count_leaves, height, validate_bst | O(n) | O(h) |
| sift_down | O(log n) | O(1) |
| build_max_heap | O(n): большинство узлов внизу, им нужно мало шагов просеивания | O(1) |
| is_max_heap | O(n) | O(1) |
| heap_sort | O(n log n) в любом случае | O(1) дополнительной памяти, сортировка на месте |

Исходное дерево получилось идеально сбалансированным (высота 4 при 15 узлах), потому что заявки добавлялись "от середины". Если добавлять их по возрастанию id, высота стала бы 15 и все операции O(h) превратились бы в O(n).

Heapsort неустойчив: заявки с равным приоритетом могут поменять порядок. Здесь это не важно, потому что при равном приоритете сравнивается id.
